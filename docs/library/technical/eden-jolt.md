## Paquete e interoperabilidad

- `jolt-physics` **1.1.1**, MIT, coincide en npm y en el release oficial. El port JoltPhysics.js usa Emscripten y publica una fábrica ESM asíncrona. `jolt-physics/wasm-compat` monohilo embebe el binario y evita resolver un recurso WASM separado. `jolt-physics/wasm` carga el binario por separado, con `locateFile` cuando el empaquetado mueve el archivo. El CMake del tag habilita `web,node,worker` y el build genera declaraciones para ambas entradas. Falta comprobar las declaraciones distribuidas con `checkJs` y la carga en Node del proyecto. La caché local devolvió `ENOTCACHED`, el registro npm no resolvió desde la terminal y la vista web del tarball no estuvo disponible. [npm](https://www.npmjs.com/package/jolt-physics) · [Release 1.1.1](https://github.com/jrouwe/JoltPhysics.js/releases/tag/1.1.1) · [README del tag](https://raw.githubusercontent.com/jrouwe/JoltPhysics.js/1.1.1/README.md) · [CMake](https://raw.githubusercontent.com/jrouwe/JoltPhysics.js/1.1.1/CMakeLists.txt) · [Generación de tipos](https://raw.githubusercontent.com/jrouwe/JoltPhysics.js/1.1.1/build.sh)
- Los componentes físicos integrados de PlayCanvas usan Ammo. El manual y `playcanvas.d.ts` 2.24.1 documentan `AppOptions.physicsWorld` y `PhysicsWorld` alpha para un backend propio. Un backend Jolt completo tendría que implementar formas, cuerpos, contactos, consultas y destrucción. La tabla oficial lista Jolt sin integración PlayCanvas. Para este corte, el cliente puede seguir aplicando las posiciones autoritativas a sus entidades de render. Jolt permanece fuera del bundle web y no requiere un backend adicional en el Engine. Las builds precompiladas de Jolt carecen de la opción para determinismo entre plataformas. [PlayCanvas, Ammo y alternativas](https://developer.playcanvas.com/user-manual/physics/ammo-alternatives/)

## Control de personaje y agua

| Opción verificada en el IDL 1.1.1 | Uso y costo |
|---|---|
| Cápsula con `CharacterVirtual` y `SetLinearVelocity` + `Update` / `ExtendedUpdate` | Resuelve contactos de movimiento contra la geometría física con más control sobre la velocidad y el apoyo en suelo. El controlador aplica explícitamente el componente vertical y el arrastre aprobados. `CharacterVirtual` no expone `ApplyBuoyancyImpulse`. Usar consultas o el perfil geométrico compartido para calcular la posición respecto de la superficie. Si se necesitan contactos entre personajes u observación por sensores físicos ordinarios, configurar la opción correspondiente de Jolt y probarla expresamente. |
| Cápsula como cuerpo dinámico y `BodyInterface.ApplyBuoyancyImpulse` | Permite que Jolt calcule empuje y arrastre de un cuerpo sumergido con superficie, normal, velocidad del líquido, gravedad y paso conocidos. La aplicación delimita primero el agua en el plano horizontal. Un movimiento directo sobre una cápsula dinámica requiere calibrar balanceo, frenado, contacto con orillas y control direccional. La API modela fuerzas sobre el cuerpo con un plano local, no una simulación de fluidos. |

Una cápsula `CharacterVirtual` es el primer experimento para nado controlado. Si el comportamiento aprobado exige que la flotación surja del empuje físico de un cuerpo, experimentar con la cápsula dinámica antes de fijar la implementación. Evitar dos solvers sobre el mismo personaje. [IDL 1.1.1](https://raw.githubusercontent.com/jrouwe/JoltPhysics.js/1.1.1/JoltJS.idl) · [Arquitectura nativa de personajes](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md#character-controller)

## Autoridad y ciclo de recursos

- Inicializar la fábrica WASM una vez por proceso Node y crear un `JoltInterface` con filtros y geometría por sala. Encapsular en el servidor la detección seca/mojada y el paso fijo acotado acumulado. El bucle actual despierta cada 50 ms y emite snapshots cada dos ticks. Conservar inicialmente ese ritmo de transporte y medir el costo de simulación y la demora visible. El servidor conserva la normalización de entradas y su caducidad y calcula el estado con el mismo perfil geométrico del río que usa el render. El shader de agua es visual. Filtrar entradas no finitas y calcular posición, altura y transiciones de lado servidor. El cliente consume un snapshot con posición, estado de nado y, si hace falta para interpolar, tiempo o secuencia. La cámara y las entidades visuales se actualizan conforme al estado recibido.
- Registrar ownership por objeto de WASM. El `JoltInterface` recibe la propiedad de sus tres filtros en el ejemplo oficial. Destruir temporales propios con `Jolt.destroy()` y respetar `AddRef/Release` para objetos compartidos. Retirar un cuerpo con `RemoveBody` y destruirlo con `DestroyBody`. Liberar personaje, cuerpo y mundo al salir o vaciar la sala, incluyendo fallo parcial de inicialización y cierre del servidor. Reusar vectores y filtros fuera de bucles calientes, evitar destruir referencias prestadas y comprobar ownership de valores devueltos en el binding. CMake declara 128 MiB de memoria lineal inicial por defecto para un build propio. Confirmar bytes reales del WASM npm, RSS y memoria libre en Node antes de dimensionar salas. [Ejemplo versionado de destrucción](https://raw.githubusercontent.com/jrouwe/JoltPhysics.js/1.1.1/Examples/proper_cleanup.html) · [Configuración de compilación](https://raw.githubusercontent.com/jrouwe/JoltPhysics.js/1.1.1/CMakeLists.txt)

## Experimento y aceptación técnica

1. Con el paquete fijado, instanciar `wasm-compat` bajo Node, verificar versión y tipos y crear un mundo pequeño. Probar paso fijo, dos salas aisladas, salida/desconexión durante la simulación y varios ciclos de crear/destruir. Registrar tiempo de arranque, p50/p95 por paso, RSS y memoria libre tras calentamiento y tras cada ciclo. El presupuesto de cada paso se contrasta con el intervalo elegido y con el costo de varias salas concurrentes.
2. Con el trazado y las reglas que se aprueben, probar cruce de orilla, retorno a seco, borde entre ramales, movimiento simultáneo, pérdida de entrada y reentrada. Verificar que posición/altura permanecen finitas y que ambos clientes coinciden en las transiciones recibidas. Repetir la caminata, monta e interacciones previas. Probar demora y cadencia de snapshots bajo latencia controlada y comparar el error visual con la base.
3. Ejecutar lint, `typecheck`, pruebas y build bajo `/Tetelestai/`. Humo de dos sesiones de navegador con teclado y táctil, capturas del cruce y cero errores de consola. Verificar en la salida y en red que el cliente no descarga Jolt. La emulación táctil cubre layout e interacción. Latencia remota, FPS y comportamiento visual de Chrome Android y Safari iOS físicos requieren sus propias mediciones.
